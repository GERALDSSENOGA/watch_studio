1. PROJECT OVERVIEW
================================================================================

WatchStudio is a watch-party web application that lets users save video links
and watch them together in synchronized rooms. It combines:

  * A personal media library (saved video links with metadata)
  * Synchronized playback rooms (YouTube IFrame API for synced play/pause/seek)
  * Real-time chat and presence per room
  * WebRTC screen sharing (host broadcasts screen/tab audio to guests)
  * Zoom-style UI (bottom control bar, collapsible sidebar, dark theme)

The platform does NOT host videos. Users submit links to existing videos
(YouTube, direct .mp4/.webm files, or third-party hosts like FullMatchShows,
Playmogo, Vixeo, Vidaraa, EmbedSeek, Bysekoze). Embeddable content plays
inside the room; non-embeddable content opens in a new tab with room chat
available for coordination.

Tech stack:
  * Next.js 16.4.2 (App Router, Turbopack)
  * TypeScript (strict)
  * Prisma ORM + PostgreSQL
  * NextAuth.js v5 (JWT sessions)
  * WebSocket server (native `ws` package, standalone process on port 3001)
  * Vitest (unit tests, 92 passing)
  * Tailwind CSS (via shadcn/ui components)
  * Docker Compose (PostgreSQL 17)

2. CORE ARCHITECTURE
================================================================================

2.1 Playback Synchronization (Host-Authoritative)

The host is the source of truth for playback state. The server persists the
authoritative state in PostgreSQL (PlaybackSession model) and relays it to all
room members via WebSocket.

Key behaviors:
  * Host commands (play/pause/seek) are sent to the server with optimistic
    concurrency (version-based). The server rejects stale commands (409).
  * Host broadcasts sync state immediately to guests (no waiting for server
    echo): currentTime (seconds), isPlaying, playbackRate, updatedAt (ms).
  * Host heartbeat: every 2.5s while playing, rebroadcasts sync state.
  * Guests apply host sync state only if drift > 1.2 seconds (avoids jitter).
  * Guests sync play/pause state with host.
  * Server-side reconciliation every 5s repairs drift for all clients.
  * New joiners receive latest playback state + latest sync state immediately.

2.2 Providers & Playback Modes

Providers are declared in lib/providers.ts with capabilities:

  Provider         Embed  Sync  Commands  External Fallback  Notes
  ----------       -----  ----  --------  -----------------  -----
  youtube          YES    YES   YES       NO                 IFrame API; only publicly embeddable videos
  direct-file      YES    NO    YES       NO                 Native <video>; local playback only
  fullmatchshows   NO     NO    NO        YES                Match replay directory; open on provider site
  playmogo         NO     NO    NO        YES                Third-party video host
  vixeo            NO     NO    NO        YES                Third-party video host
  vidaraa          NO     NO    NO        YES                Third-party video host
  embedseek        NO     NO    NO        YES                Third-party video host
  bysekoze         NO     NO    NO        YES                Third-party video host
  generic          NO     NO    NO        YES                Fallback for everything else

Playback modes (stored on MediaItem):
  * SYNCHRONIZED — embedded player with host-controlled sync (YouTube only)
  * EXTERNAL — external link or native video; no sync; chat coordination
  * UNSUPPORTED — not playable (rare, after provider logic)

2.3 WebRTC Screen Sharing

  * Host captures screen via getDisplayMedia({video: true, audio: true}).
  * Host creates one RTCPeerConnection per guest (mesh topology).
  * WebSocket relays SDP offers/answers and ICE candidates.
  * Host controls: Mute/Unmute (audio track), Volume (guests only), Fullscreen,
    Stop Sharing.
  * Persistent "Live" badge while sharing; audio muted indicator.
  * Screen share state persists in a global React Context (ScreenShareProvider)
    so it survives page navigation. On re-entering a room, the host re-broadcasts
    screen-share.started and re-creates peer connections with existing members.
  * Browser STUN servers used; TURN recommended for production (NAT traversal).

5. API ENDPOINTS
================================================================================

HTTP (Next.js Route Handlers):

  GET/POST   /api/media              List / create media items
  GET/PATCH/DELETE /api/media/[id]   Read / update / delete media item
  GET        /api/rooms              List user's rooms
  POST       /api/rooms              Create room
  GET/PATCH/DELETE /api/rooms/[id]   Room CRUD
  DELETE     /api/rooms/[id]/member/[userId]  Remove member
  GET/POST   /api/playback/[roomId]  Get state / send playback command
  GET        /api/chat/[roomId]      Chat history
  POST       /api/invitations        Create invitation
  GET        /api/invitations/[token] Accept invitation
  POST       /api/invitations/revoke Revoke invitation
  GET        /api/me                 Current user
  POST       /api/auth/register      Register
  GET/POST   /api/auth/[...nextauth] NextAuth handlers
  GET        /api/reports            Report media/link
  GET        /api/matches            Proxy to worldcup26.ir football API

WebSocket (ws.mts, port 3001):

  Client -> Server:
    {type:"auth", token}                      Authenticate
    {type:"room.join", roomId}                Join room
    {type:"chat.send", roomId, body}          Send chat message
    {type:"playback.command", roomId, command} Host play/pause/seek
    {type:"playback.reconcile", roomId, version} Request state sync
    {type:"playback.sync", ...}               Host broadcast sync state
    {type:"webrtc.offer/answer/ice-candidate"} WebRTC signaling
    {type:"webrtc.screen-share.started/stopped"} Screen share status

  Server -> Client:
    auth.ok / auth.error
    room.joined (with presence)
    presence.joined / presence.left
    chat.message
    playback.state (authoritative)
    playback.sync (host broadcast)
    playback.sync.state (latest sync for new joiners)
    playback.error
    webrtc.* (relayed between peers)

8. KNOWN LIMITATIONS & PRODUCTION CONSIDERATIONS
================================================================================

  * WebRTC mesh topology: host opens N peer connections for N guests.
    Scales to ~5-10 guests. For larger rooms, use SFU (MediaSoup/LiveKit).
  * Third-party video hosts (playmogo, vixeo, etc.) block iframe embedding.
    They open in a new tab; room chat is used for coordination.
  * Screen sharing requires HTTPS (getDisplayMedia browser requirement).
  * Prisma migration permission issues on some Windows setups — run
    prisma generate / migrate manually if needed.
  * No user avatar upload yet (names only in presence).
  * No playlist/queue yet (one media item per room).
  * Rate limiting on HTTP only; WebSocket connections not rate-limited.
